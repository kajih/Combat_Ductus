# Reconnecting or joining mid-Match inherits current state; slots are never reserved

When a connection claims a player slot — the initial Player 1/Player 2 assignment, or taking over one freed by an earlier disconnect (see `second-client-controls-player-two.md`) — it inherits whatever state that slot's Character is already in: current Health, position, and the Match's current status, with no fresh-start reset. This is deliberate, not an oversight: if reconnecting reset a Character's Health, a losing player could escape a bad position simply by disconnecting and reconnecting, undermining the terminal, no-rematch-mid-Match design of a Match (`CONTEXT.md`'s `Match` entry) — the only sanctioned way back to a fresh state is the explicit restart control (`restart-match.md`), never an implicit one triggered by a connection event. Following from that, a disconnected player's slot is never reserved for their return — it's freed the instant they disconnect and claimed by whoever connects next, first come first served, since a Character's Health and position belong to the slot (the ongoing duel), not to any specific network connection's identity. A connection arriving once both player slots are already taken becomes a spectator (see `second-client-controls-player-two.md`) rather than being refused or queued — no separate "server full" case exists. A connection arriving after the Match has already ended simply receives the truthful `MatchStatus::Ended` in its very first snapshot, which the client's state machine already reacts to generically (the same code path that ends an in-progress Match for everyone already connected) — so it lands on the Match-Ended screen within a frame or two of connecting, with no special-casing needed for a "joined late" case.
